# Use a durable two-layer workflow runtime

The database owns workflow and job state; `python-statemachine` validates and expresses allowed transitions in memory rather than maintaining a second persisted state. Workflow definitions live in versioned Python code with a stable definition key, definition version, and payload schema version; a Workflow Run binds the definition version used to create it, so code upgrades change only new runs. The database records runs, jobs, steps, checkpoints, and outcomes rather than acting as a generic workflow engine. A Workflow Run is one business-process instance and schedules Jobs; Jobs own steps and checkpoints and report completion back to the Workflow Run. Chapter-quality and Bible graphs run under LangGraph with PostgreSQL checkpoints and correlation IDs, so a process failure can resume inside the graph instead of only at an outer job boundary. Jobs are claimed transactionally through PostgreSQL and every step has a stable idempotency key. Domain state changes and their events are committed atomically to an append-only event outbox; SSE is at-least-once and consumers deduplicate by event ID. Pause and cancel are cooperative control requests evaluated at safe checkpoints; a model call may finish or time out, but its result does not advance normal state after cancellation.

Failures are classified as transient, permanent, cancelled, timeout, quota exhausted, or upstream invalid, and only transient failures retry automatically. Job and Workflow Run terminal states are immutable; recovery creates a new attempt or run rather than reopening history. Job state is limited to `ready`, `leased`, `running`, `pause_requested`, `paused`, `cancel_requested`, `cancelling`, `interrupted`, `succeeded`, `failed`, `cancelled`, and `skipped`; Workflow Run state uses its business-facing subset. Every Job Type has database-owned timeout, heartbeat, retry, and backoff settings.

PostgreSQL also enforces idempotency keys, state enum checks, unique pending Review Items, unique current-canonical pointers, and immutability rules for versioned records. Each Job attempt receives a monotonic fencing token, and checkpoint or artifact writes must carry the current token so a stale Worker cannot overwrite a newer attempt. Worker concurrency is configurable, but defaults to one and always serializes work within a project through database locking. The public API exposes domain actions such as pause, resume, cancel, approve, and request-revision rather than generic state PATCHes. Alembic is the only schema-change mechanism, and seed data is limited to default Mock/model/job configuration rather than sample projects.

The Worker uses short PostgreSQL polling as the authoritative queue mechanism, with LISTEN/NOTIFY allowed only to wake it sooner. It stops claiming work on SIGTERM, requests cooperative cancellation for active Jobs, waits up to the graceful timeout, and records an interrupted checkpoint if it must exit first.

The framework is accepted only after the deterministic fake model provider completes project creation, Bible publication, chapter workflow, progress observation, pause/resume/cancel, candidate review, memory projection, Markdown/TXT export, and event replay without external model access.

## Consequences

The runtime is more explicit and checkpoint-heavy than a minimal script, but it makes long-running generation auditable, resumable, and safe to interrupt. Multiple workers can be introduced later without changing the persistence contract.
